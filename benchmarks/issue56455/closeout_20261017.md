## 当前可以支持的结论

1. **#56455 的重点是改变 prefill 的进入节奏，以形成有界的 prefill wave 和更多 decode-only 批次。**PR 作者希望提高纯 decode 批次比例，从而在其测试配置下更多使用 full CUDA Graph，减少小块 prefill 持续混入造成的混合执行开销。PR 报告的 ShareGPT、Qwen2.5-7B-Instruct、2000请求、并发256测试中，吞吐由20.15升至23.04 req/s（+14.32%）；同时 P99 ITL 从87.70升至252.28 ms（+187.65%）。这是该 PR 自己报告的性能与尾延迟取舍，不是我们独立复现的结论。

2. **H100 复现没有显示出原报告中的吞吐提升，但不能直接否定原结果。**此前 H100 运行的工作负载与 PR 基准并不相同。运行中观察到的约88 ms是相邻非空 SSE 流事件间隔的 P99 近似量，不是经过同一口径计算的逐 token ITL，不能与原报告的252.28 ms直接比较。可说“在我们的负载下未复现报告的吞吐增益”，不能说“证明 PR 没有效果”。

3. **3070 Ti 上的固定448试验只显示小幅、场景相关的变化。**64请求、每个负载三轮的固定到达对照中，吞吐中位数变化为：同负载 +0.31%，轻负载 +0.02%，重负载 +0.69%；TTFT P99 分别约下降2.65%、3.45%、2.24%，SSE gap P99 代理分别约下降9.29%、8.15%、9.72%。这些结果显示该局部规则在这组小模型/小卡负载下没有明显伤害，但收益小，且不能代表 #56455 的 wave 策略或 H 系列结果。SSE gap 是流事件间隔代理，不等同于逐 token ITL。

4. **等待队列诊断把下一项研究方向缩小到序列名额占用，但没有证明硬件上限。**在固定重负载、`max_num_seqs=8` 的单次 trace 运行中，按请求累计的等待区间大部分被归因为 `sequence_capacity`；`prefill_cap` 占比很小。8 是该实验的服务配置。结果说明等待请求常遇到序列名额已满，不代表 GPU、KV cache 或该机器的实际能力已经达到上限，也不说明增加 `max_num_seqs` 一定有益。trace 开启时的时延不能作为性能比较。

5. **本地 CUDA Graph 捕获覆盖不足以解释原 PR 的机制。**本地诊断服务配置记录的 capture sizes 为 `[1, 2, 4, 8, 16]`，而固定448会产生远大于16 token 的混合批次；按当前分发逻辑，这些批次可能没有匹配到已捕获图而回退到 `NONE`。因此本地固定 cap 结果没有验证“piecewise 混合执行相对 full decode graph”的收益。精确的各步 graph mode 与执行时间尚未完成关联。

## 可发在 #56455 讨论区的英文草稿

> Thanks for sharing the implementation and benchmark details. We have been investigating the same scheduling trade-off: admitting prefills in bounded waves can create more decode-only batches, while delaying resident decodes can worsen tail inter-token latency.
>
> In your reported ShareGPT run, throughput increased from 20.15 to 23.04 req/s, while P99 ITL increased from 87.70 ms to 252.28 ms. That makes the decode-tail trade-off an important part of evaluating this policy.
>
> We ran a separate H100 workload but did not reproduce the reported throughput gain. The workload was not identical to the PR benchmark, so we do not interpret this as disproving the result. Our approximately 88 ms P99 measurement was based on gaps between non-empty SSE events, not the same per-token ITL measurement, and is therefore not directly comparable to the reported 252.28 ms.
>
> We also ran smaller fixed-arrival experiments on a 3070 Ti. A fixed prefill-token cap produced only modest, workload-dependent changes, and those runs do not validate the CUDA Graph mechanism described in this PR. We are pausing our independent implementation for now because reproducing the result faithfully requires matching the workload and verifying the actual graph mode used by each batch.
>
> One question that would help us interpret the reported gain: were the mixed prefill/decode batches dispatched to piecewise CUDA Graphs, while decode-only batches used full CUDA Graphs for this benchmark? If available, per-step graph-mode counts or timings would help separate the scheduling effect from the graph-path effect.
